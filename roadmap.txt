GOAL
----
Headless, high-performance media server replacing the embedded HTTP server in
the macOS app (xcode-TM-Sonder/). Two deployment paths, both Docker-free:

  1. Bare-metal arm64 binary via launchd (max performance, direct disk, VideoToolbox)
  2. Apple Containerization micro-VM (`container` CLI) for isolation/portability

Target client compatibility: existing iOS client (IOS_Client_Xcode) must pair
and play against this server UNCHANGED. Wire contract source of truth:
API.md + Packages/SonderAPI/Sources/SonderAPI/.

DESIGN DECISIONS (LOCKED)
-------------------------
- Language: Go 1.25, ZERO third-party dependencies (stdlib only). Rationale:
  CGO_ENABLED=0 static binaries, trivial linux/arm64 cross-compile for
  containers, no supply chain.
- Storage: JSON snapshot file (mirrors Swift app's library.json approach),
  atomic write via temp+rename, debounced saves. SQLite (modernc.org, pure-Go)
  is a later upgrade if catalog size demands it.
- Streaming: http.ServeContent over *os.File (kernel sendfile fast path,
  correct Range/If-Range/206 semantics for AVPlayer).
- Transcoding: ffmpeg sidecar, fragmented MP4 to stdout
  (-movflags frag_keyframe+empty_moov), per-session process killed via request
  context on client disconnect. Remux mode (stream-copy mkv->fMP4) as the
  fast path before full re-encode.
- Auth: peer-address based (r.RemoteAddr host, never Host header). Loopback
  bypass; Bearer token or ?token= fallback; LAN gate. Identical semantics to
  API.md "Auth" section.
- Track IDs keep Swift conventions: embedded-audio:N / embedded-subtitle:N /
  sidecar:N so the iOS client logic works unmodified.

POST-MVP NOTES
--------------
- Container networking: all container traffic arrives from the bridge peer,
  so loopback bypass never applies inside a VM — LAN mode + pairing token is
  the supported container posture.
- Transcode warm-session position does not advance with playback time; the
  30s attach window is measured from spawn position.
